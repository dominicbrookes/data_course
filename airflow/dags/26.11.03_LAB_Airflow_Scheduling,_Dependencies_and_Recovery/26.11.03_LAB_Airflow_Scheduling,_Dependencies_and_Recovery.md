Q. 2 — Compare catchup=True and catchup=False

A daily DAG has: start_date = 2026-08-01, today = 2026-08-05

Explain what may happen when: catchup=True, catchup=False

========================================================================
ANSWER Q2
========================================================================

catchup=True

With `start_date = 2026-08-01` and a daily schedule, the scheduler works out that runs were due for 1, 2, 3 and 4 August. Airflow records every DAG run in the metadata database, so the scheduler checks there to see which of those runs have already happened. With `catchup=True`, it creates a run for each missed day, up to four runs (1–4 Aug), each for its own date. 


====================================

catchup=False

The DAG will just run in alignment with whatever the cron is in the schedule. It will not run for previously missed days, apart from the most recent one (4 Aug), and then carries on as normal.


========================================================================

Q. 3 — Plan a Three-Day Backfill

A sales DAG missed: 2026-08-02, 2026-08-03, 2026-08-04

Write a safe backfill plan.

Include:

date order;

duplicate check;

validation after each date.

========================================================================
ANSWER Q3
========================================================================

The runs must go in date order, oldest to newest, because later days may depend on earlier ones. For example, running totals need the previous days in place, and the most recent data should be loaded last so it isn't overwritten by older data. In SQL, this also protects PK and FK relationships.

After each catchup run, a check should be made for duplicate data. As the runs were missed, there shouldn't be duplicate data, but a failed run may have partly written data before it stopped. If there are duplicates, they should be removed through a transform or in SQL.

After each date, the output should be validated before moving on to the next one. This means checking that the row count matches the source for that date, that business totals such as daily sales match the source figures, and that each order ID appears only once. In SQL, a primary key enforces this automatically, as the database will reject a duplicate PK.

Ironhack:

Confirm source data exists for all three dates.
Check whether partial output already exists.
Run 2026-08-02.
Validate row counts and business totals.
Run 2026-08-03.
Validate again.
Run 2026-08-04.
Validate again.
Confirm the job can be rerun without creating duplicates.

Q. 18 — Recover from a Failed Historical Run

A run for 2026-08-03 failed at transform.

States: extract = success, transform = failed, validate = upstream_failed, publish = upstream_failed

Write the recovery steps.

========================================================================
ANSWER Q18
========================================================================

1. Open the 2026-08-03 run in the Airflow UI and check the transform logs to find the first useful error.
2. Fix the cause of the error (e.g. the code, or the input data).
3. Check whether transform partly wrote any output before it failed, and remove it if so, to avoid duplicates.
4. Clear transform for the 2026-08-03 run, including its downstream tasks, so transform, validate and publish run again.
5. Do not re-run extract, as it already succeeded.
6. Once publish succeeds, validate the 2026-08-03 output (row counts and totals) before relying on it.

Q. 19 — Find the Backfill Risk

A daily task writes: INSERT INTO daily_sales ...

every time it runs.

A backfill runs the same date twice.

What risk exists, and what should be checked before the backfill?

========================================================================
ANSWER Q19
========================================================================

Risk: INSERT adds new rows every time it runs, so running the same date twice would load that day's sales twice. This creates duplicate rows and doubles the totals for that date, so any report built on daily_sales would be wrong.

Before the backfill, check whether daily_sales already has rows for the dates being backfilled (e.g. SELECT COUNT(*) FROM daily_sales WHERE sale_date = '2026-08-03'). If it does, either delete that date's rows first and then insert, or change the load so it updates existing rows instead of adding new ones. This makes the task safe to rerun for the same date without creating duplicates. If daily_sales has a primary key, a duplicate would be rejected and the load would fail instead.
